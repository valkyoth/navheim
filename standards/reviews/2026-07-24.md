# Standards Source Review — 2026-07-24

Status: acquisition baseline review; not a conformance claim

## Outcome

The v1.0 roadmap is represented by 36 source families in
`standards/sources.toml`. The review checked publisher authority, current
landing-page revision markers, access class, planned Navheim ownership, first
implementation milestone, and whether bytes may be downloaded automatically.

The networked marker review passed for 14 official source families. Seventeen
explicit public downloads were fetched into the ignored local vault and
SHA-256 locked. The 25 supporting IETF RFCs and all 210 RFC Editor errata
visible for them matched the tracked source/errata baseline.

## Current Findings Incorporated

- GPS civil decoding uses IS-GPS-200N, IS-GPS-705J and IS-GPS-800J together
  with each document's `-003` interface revision notice. An original
  specification without its IRN is not the current baseline.
- Galileo Open Service uses OS SIS ICD 2.2. OSNMA uses SIS ICD 1.1, Receiver
  Guidelines 1.3, IDD ICD 1.1, PKI CP/CPS 1.1 and SDD 1.0. HAS uses SIS ICD
  1.0; registration-gated IDD material remains manual.
- QZSS current public markers include PNT-006, L1S-009, L6-008, MDC-004 and
  SAS-001. Their click-through terms make the documents manual/local-only.
- NavIC uses L5/S SPS ICD 1.1, L1 SPS ICD 1.0 and the NeQuick-N material.
- RTCM 10403.4 must be read with Amendment 1 dated 2024-11-01. RTCM 10402.3
  remains necessary for the roadmap's explicit legacy DGNSS profile.
- NMEA still identifies 0183 4.30 as current. NMEA/SAE semantics remain
  licensed and cannot be reconstructed from unofficial tables.
- RINEX 4.02 is current for the new navigation-record baseline; RINEX 2.11 and
  3.05 remain necessary for promised archive compatibility. ANTEX 2.0 is the
  current inventory candidate rather than silently assuming an older profile.
- OMA's release tree exposes SUPL 2.0.6, 2.1 and 3.0 lines. The v0.187.x
  profile-freeze must decide exact ULP/ILP messages and versions instead of
  calling a single historical PDF “SUPL support.”
- 3GPP TS 37.355 Release 19 version 19.3.0 was current at review time. Device
  compatibility may require older release profiles, which must be named.
- ITU-T X.680/X.691 (02/2021), FIPS 186-5 and SP 800-186 remain current
  candidates for the bounded PER and GNSS-authentication adapter boundaries.
- The architecture-wide audit added primary-source families that the earlier
  protocol-focused inventory omitted: BIPM/CCTF/ITU-R GNSS time transfer,
  Rust platform contracts, SDR/FPGA device stacks, Linux/BSD, Microsoft and
  Apple I/O, NovAtel, and conditionally admitted receiver protocols.
- The fourth gap review added a profile-freeze source family for optional
  scintillation, reflectometry, space-weather and remote-sensing methods.
  ITU-R P.531-16 is an in-force starting point; v0.124.1 must select exact IGS
  and other authoritative algorithm, calibration and validation records before
  any scientific behavior is implemented.
- The fifth gap review added a numerical-methods profile-freeze family.
  Netlib's current LAPACK 3.12.1 documentation supplies factorization,
  least-squares and condition-estimation reference behavior, while NIST DLMF
  Chapters 7 and 8 supply the error/incomplete-gamma functions underlying the
  admitted normal and chi-square kernels. Exact methods and independent
  high-precision tables must be frozen at v0.3.4-v0.3.5.
- The sixth review required no new source family: UTC/calendar and TT/UT1
  work belongs to the existing time-transfer and IERS/IAU families; multicore
  and snapshot contracts use the Rust/platform family; and receiver control
  stays inside exact vendor hardware/firmware profiles. Each new milestone
  must split those families into exact manifest records before implementation.
- The seventh review also required no new family. DSP/geo numerical behavior
  remains under the numerical and IERS/IAU families; snapshot sealing uses the
  existing cryptographic/platform-authority sources; and configuration
  generations refine the existing exact receiver firmware/control profiles.
- The eighth review requires no new family. Geo/navigation ownership and
  executor borrowing remain implementation contracts under the existing
  numerical and Rust/platform families; snapshot AEAD/keystore adapters refine
  the cryptographic/platform-authority family; and independent configuration
  assessment must use the same exact receiver hardware/firmware profiles plus
  observable output/time-pulse/correction evidence.
- The ninth review requires no new family. Prepared SDR transitions and sample
  generation/read evidence refine the SDR/device-stack profiles; cooperative
  cancellation remains a Rust/platform contract; and the common snapshot
  protection lifecycle plus separate Linux/BSD, Windows, Apple and Android
  adapters refine the existing cryptographic and platform families. The
  platform source scopes now explicitly require exact keystore, key-custody,
  protected-persistence, nonce/counter and lifecycle documents before their
  respective v0.189.3-v0.189.6 stops.
- The tenth review requires no new family. It makes the existing contracts
  implementable and their claims auditable: the Rust/platform family must
  support separate non-escaping borrowed jobs and owned lease handles with
  explicit ownership states; SDR/device profiles must expose partial and
  unknown mutation plus per-device coherent-group evidence; and snapshot
  profiles now treat authenticity, confidentiality and freshness as three
  independent dimensions. Each platform profile must separately evidence
  cryptographic verification, durable commit, trusted monotonic comparison
  and update, crash recovery, and key/counter migration. Atomic file
  replacement plus valid AEAD is only crash-consistent; absent a qualified
  monotonic authority, rollback resistance remains unavailable.
- The eleventh review also requires no new family or milestone. The
  Rust/platform profile must now support the exact fail-stop destruction
  contract for a nonterminal `ExecutionHandle`, including panic unwinding and
  explicit join/cancel-and-join ownership return. SDR/device profiles must
  preserve the originating apply error and bounded transition/rollback/reprobe
  evidence; post-submission uncertainty or evidence overflow is state-unknown,
  never no-mutation. Snapshot profiles narrow `CounterChecked` to comparison
  with named non-rollback-resistant local state. A rollback-resistant claim
  additionally requires documented atomic digest-bound compare-and-advance or
  an exclusive expiring writer reservation spanning seal, durable commit and
  monotonic advance, with concurrent-writer and crash recovery evidence.
- The twelfth review likewise strengthens existing owners without adding a
  source family or release. Executor evidence must cover destructor elision:
  the authoritative registry retains forgotten/leaked handle jobs and capacity
  until explicit shutdown, executor drop with registered work uses concrete
  `std::process::abort()`, and soundness never depends on `Drop`. SDR/device
  profiles must support structural success evidence and positive no-mutation
  proof while keeping those adapter assertions separate from observed
  consistency. Snapshot authority profiles must create a distinct,
  suite-approved, domain-separated binding over the exact canonical protected
  envelope; corruption/artifact digests are not substitutes, and reservation
  expiry/reboot recovery comes only from authority monotonic/boot-generation
  evidence.
- The thirteenth review adds no family or milestone. The executor's Rust
  contract now requires linearizable, generation-safe retirement so completion,
  drop, result claim and shutdown have one atomic winner and cannot suffer ABA;
  pre-abort memory status is not durable evidence. SDR/device profiles must
  distinguish a framework-issued pre-submission no-command token from physical
  stability, which additionally requires an exclusive control lease and an
  exact no-autonomous-change profile. Snapshot platform evidence must support
  the normative durable Pending -> AuthorityCommitted -> Committed protocol
  around candidate staging and promotion, with exclusive recovery at every
  crash point and no success after authority commit if promotion remains
  incomplete.
- The fourteenth review also strengthens existing owners without adding a
  family or milestone. The Rust/platform profile must linearize dispatch
  against cancellation-before-dispatch, keep handle `Drop` to one retirement
  CAS, run sealed result/lease/trace cleanup separately, test panicking and
  reentrant cleanup, and retire slots rather than wrap exhausted generations.
  Snapshot platform profiles must implement the common
  `Committed`/`Pending`/`AuthorityCommitted`/`PromotedUnfinalized`/
  `CorruptOrUnknown` restore-and-writer matrix, bounded per-namespace
  candidates/retention/retries, and deterministic cancellation/supersession
  cleanup without deleting unresolved authoritative state.
- The fifteenth review again adds no family or milestone. The Rust/platform
  profile must expose caller-driven, receipt-bounded executor cleanup progress
  and admission backpressure without a hidden reaper, make the executor
  must-use, couple lifecycle and payload initialization, prefer safe ownership
  storage and exclude unsafe `ManuallyDrop` extraction from the 1.0 executor.
  Miri, Loom and Kani evidence respectively covers destruction/panic,
  publication/cleanup and exactly-once ownership. Snapshot platform profiles
  may expose a separate repair capability only for exact-current candidate
  recovery or durable old-namespace retirement followed by a fresh-domain
  continuity break with anti-revival, authorization and invalidation evidence.
- The sixteenth review adds no family or milestone and corrects the v0.48.3
  Rust API rather than relaxing handle lifetimes. Cleanup takes a shared
  executor borrow so it remains callable while unrelated handles are live.
  Synchronized interior state admits exactly one cleaner through a private
  atomic guard; contention returns pre-mutation `Busy`, eligible entries use a
  bounded lowest-`JobId` order, and callers cannot receive, leak or forget the
  guard. Loom must cover cleanup against completion, claim, handle drop,
  admission, another cleanup caller and shutdown.
- The seventeenth review adds no family or milestone and separates v0.48.3
  cleanup-state mutation from trace mutation. Validation and `poll_cleanup`
  remain mutation-free on `Busy`; the failed cleaner CAS creates a bounded
  private contention receipt. The replayable profile requires the supervisor
  to bind that receipt to a caller lane/logical call in the bounded trace
  before reacting. Trace overflow uses the existing fail-closed policy, replay
  reproduces `Busy` without live contention, and omission is admitted only for
  a `PlanReceipt` profile proving contention semantically inert.
- The eighteenth review adds no family or milestone and closes the safe-Rust
  enforcement gap left by `#[must_use]`. Replayable application code receives
  only `ExecutionSupervisor::poll_cleanup`; the receipt-producing executor
  primitive and contention receipt remain crate-private. The supervisor binds
  one executor/plan/trace generation, advances the planned lane call, records
  contention before returning observable `Busy`, returns trace-unavailable or
  stops on recording failure, and consults replay before any live cleaner CAS.
  Even a proved semantically inert profile remains behind this boundary.
- The nineteenth review adds no family or milestone and removes ambient
  concurrency identity from v0.48.3. `PlanReceipt` privately issues bounded,
  must-use, non-cloneable `CleanupLane` capabilities with deterministic IDs,
  checked non-wrapping per-lane call sequences and supervisor/executor/plan/
  trace-generation binding. Mutable lane use prevents safe same-lane
  concurrency, distinct planned lanes remain concurrent, and trace/replay keys
  exact `(CleanupLaneId, CallSequence)` pairs rather than arrival, CAS, OS
  thread or runtime-task order. Exhaustion and fresh-generation renewal are
  bounded and tested.
- CGGTTS V2E is the required multi-GNSS interchange baseline for common-view
  and all-in-view timing. The profile freeze must include the public BDS-3
  extension and then recheck current BIPM processing/submission guidance and
  in-force ITU-R TF.767/TF.686 revisions.

## Manual/Local-Only Work Still Required

The following absence is intentional, not evidence that the documents are
optional:

- RTCM, NMEA, ICAO, RTCA, EUROCAE and SAE licensed baselines;
- QZSS consent-gated downloads;
- Galileo registration-gated HAS distribution material;
- exact GLONASS and BeiDou language/revision sets after a human document
  identity review;
- OMA SUPL release packages and 3GPP release archives after the owning profile
  matrix is chosen;
- IERS/IAU/WGS 84/EPSG material selected by exact coordinate/time profile;
- u-blox, Septentrio and other receiver documents tied to frozen
  hardware/firmware profiles.
- SDR driver, firmware, FPGA/bitstream and platform ABI/API documents tied to
  exact admitted devices and operating-system releases;
- BIPM/ITU-R time-transfer material and every conditional vendor receiver
  profile before its named implementation milestone.
- exact GNSS science algorithms, calibration procedures and validation
  datasets selected by the v0.124.1 profile freeze.
- exact numerical algorithms, error analyses and independent arbitrary-
  precision tables selected by the v0.3.4-v0.3.5 profile freezes.

No implementation milestone may proceed by substituting unofficial mirrors or
remembered tables for these sources.

## Reproduction

Offline:

```text
scripts/verify-rfcs.sh
python3 scripts/test-rfc-sources.py
python3 scripts/rfc_errata.py
python3 scripts/standards-sources.py check
python3 scripts/test-standards-sources.py
python3 scripts/standards-sources.py verify-local --require-downloads
```

Networked:

```text
python3 scripts/rfc_errata.py --live
python3 scripts/standards-sources.py review-current
```

Before code relies on a family, repeat the official-page review, inspect
revision history and errata, lawfully acquire the exact bytes, and split the
family into exact `standards/manifest.toml` conformance records.
